**Findings on `aws_iam_policy_document.pass` (lines 42–56)**

1. **What is misconfigured**  
   The `Allow` statement grants the write actions `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable` with `resources = ["*"]`. This gives unrestricted resource scope for these sensitive, write-capable actions.

2. **Why it matters**  
   If this policy document is attached to an IAM identity, that identity could create or modify Lambda functions, event source mappings, and DynamoDB tables anywhere in the account. That is unconstrained write access: it can alter application behavior, create persistence, disrupt workloads, or be abused as a step toward wider compromise.

3. **How to fix safely**  
   Replace `"*"` with specific ARNs or constrained ARN patterns for the resources the identity actually needs to manage. For example:
   - Lambda functions: `arn:aws:lambda:<region>:<account>:function:<prefix>-*`
   - Event source mappings: `arn:aws:lambda:<region>:<account>:event-source-mapping:*`
   - DynamoDB tables: `arn:aws:dynamodb:<region>:<account>:table/<prefix>-*`

   Use separate statements if different actions need different resource scopes.

**Findings on `aws_iam_policy_document.fail` (lines 60–73)**

1. **What is misconfigured**  
   The `Allow` statement grants `s3:GetObject` and `iam:CreateAccessKey` with `resources = ["*"]`. Both are highly sensitive actions and are not constrained to any specific S3 bucket, object, or IAM user.

2. **Why it matters**  
   - `s3:GetObject` on `*` can allow reading objects from any S3 bucket/object the policy can reach, enabling data exfiltration.
   - `iam:CreateAccessKey` is a permissions-management/credential-exposure action. With `*`, it can allow creating access keys for any IAM user in the account. If used against a privileged user, that can lead to privilege escalation or persistent credential exposure.

   Combined, these permissions are especially dangerous because an actor could both read sensitive data and create new credentials for further access.

3. **How to fix safely**  
   Split the permissions into least-privilege statements:
   - Restrict `s3:GetObject` to the exact bucket and object prefix required, for example:  
     `arn:aws:s3:::app-data/read/*`
   - Remove `iam:CreateAccessKey` unless it is absolutely required. If it is required, restrict the resource to a specific IAM user ARN, for example:  
     `arn:aws:iam::<account>:user/<specific-user>`
   - Add conditions where appropriate, such as IP allowlists, MFA, or tag-based constraints.

Avoid `"*"` as a resource for any action that is write-capable, read-sensitive, or IAM-related.
