**Misconfiguration**
Two IAM policy documents grant overly permissive access by using `"*"` as the resource:
1. `aws_iam_policy_document.pass` (lines 42-56): Grants `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable` on `"*"`.
2. `aws_iam_policy_document.fail` (lines 60-73): Grants `s3:GetObject` and `iam:CreateAccessKey` on `"*"`.

**Security Risk / Blast Radius**
*   **Credentials Exposure & Privilege Escalation:** Granting `iam:CreateAccessKey` on `"*"` allows the principal to create long-term access keys for *any* IAM user in the account. The principal could generate keys for an administrative user, escalating their own privileges and exposing credentials.
*   **Data Exfiltration:** Granting `s3:GetObject` on `"*"` allows the principal to read objects from *any* S3 bucket in the account.
*   **Unbounded Write Access:** Allowing Lambda and DynamoDB creation actions on `"*"` violates least privilege by not constraining where resources can be created.

**How to Fix Safely**
Replace the wildcard `"*"` resource with specific Amazon Resource Names (ARNs) to enforce least privilege:
*   **`aws_iam_policy_document.fail`:** Scope `s3:GetObject` to specific bucket ARNs (e.g., `arn:aws:s3:::specific-bucket/*`). Scope `iam:CreateAccessKey` to specific IAM user ARNs, or remove the action entirely if it is not strictly required.
*   **`aws_iam_policy_document.pass`:** Scope the actions to specific Lambda and DynamoDB ARNs. If exact names are unknown at creation time, restrict the ARNs to the specific account and region (e.g., `arn:aws:dynamodb:us-east-1:123456789012:table/*`).
