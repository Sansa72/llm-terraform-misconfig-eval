The `aws_iam_policy_document.pass` (lines 42–56) and `aws_iam_policy_document.fail` (lines 60–73) each trigger multiple checks because their `statement` blocks grant broad permissions on `"*"` resources without any conditions.

**Findings on `aws_iam_policy_document.pass` (lines 42–56)**

- **CKV_AWS_111 – write access without constraints**  
  The statement (lines 44–54) allows `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable`. These are write actions, and the rule requires that write access be constrained. The policy provides no constraints: `resources` is `["*"]` (line 52) and there is no `condition` block.

- **CKV_AWS_356 – `"*"` resource for restrictable actions**  
  The same statement uses `"*"` as the resource for actions that can be restricted to specific ARNs (the three listed actions). The rule prohibits `"*"` in the `resources` field for such actions. The offending field is `resources = ["*"]` at line 52.

**Findings on `aws_iam_policy_document.fail` (lines 60–73)**

- **CKV_AWS_108 – data exfiltration**  
  The statement (lines 63–71) includes `s3:GetObject` with `resources = ["*"]` (line 70). This action can read objects from any S3 bucket, which the rule flags as a data exfiltration risk.

- **CKV_AWS_107 – credentials exposure**  
  The same statement includes `iam:CreateAccessKey` with `resources = ["*"]`. This action can create access keys for IAM users, potentially exposing long-term credentials. The rule flags it as a credentials exposure risk.

- **CKV_AWS_356 – `"*"` resource for restrictable actions**  
  Both `s3:GetObject` and `iam:CreateAccessKey` are restrictable actions, yet the statement’s `resources` field (line 70) is `["*"]`. The rule requires that `"*"` not be used for such actions.

- **CKV_AWS_109 – permissions management / resource exposure without constraints**  
  `iam:CreateAccessKey` is a permissions management action. The statement allows it on `"*"` resources with no conditions, violating the rule that such actions must be constrained.

- **CKV_AWS_110 – privilege escalation**  
  `iam:CreateAccessKey` can be used to escalate privileges (e.g., by creating keys for a privileged user). The statement allows it on `"*"` resources without constraints, which the rule flags.

**Remediation guidance**

- For `aws_iam_policy_document.pass` (lines 42–56):  
  To resolve CKV_AWS_111 and CKV_AWS_356, change the `resources` field at line 52 from `["*"]` to a list of the specific resource ARNs that the actions should target. If the actions must remain broad, add a `condition` block to the statement to restrict access (e.g., by source IP, VPC, or tags).

- For `aws_iam_policy_document.fail` (lines 60–73):  
  - To resolve CKV_AWS_108, restrict `s3:GetObject` by changing the `resources` field (line 70) from `["*"]` to the ARNs of the specific S3 buckets/objects that need to be read.  
  - To resolve CKV_AWS_107, CKV_AWS_109, CKV_AWS_110, and CKV_AWS_356, either remove `iam:CreateAccessKey` from the `actions` list (line 66) or change the `resources` field (line 70) from `["*"]` to the ARNs of the specific IAM users for which keys may be created, and add a `condition` block to further constrain the access.  
  - Additionally, for CKV_AWS_356, ensure that after restricting the actions, the `resources` field no longer contains `"*"` for any restrictable action.
