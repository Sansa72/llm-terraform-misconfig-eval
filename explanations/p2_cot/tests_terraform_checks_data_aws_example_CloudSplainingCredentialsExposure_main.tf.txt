The scanner flagged two IAM policy documents in your Terraform file: `aws_iam_policy_document.pass` and `aws_iam_policy_document.fail`. Both policies use `"*"` as the resource, which grants unrestricted access to all resources in the account for the specified actions. This violates AWS best practices and multiple security checks. Below is a breakdown of each finding and how to fix it.

---

### 1. `aws_iam_policy_document.pass` (lines 42–56)

**Flagged checks:**
- **CKV_AWS_111** – IAM policy should not allow write access without constraints.
- **CKV_AWS_356** – IAM policy should not use `"*"` as a resource for restrictable actions.

**Why it’s a problem:**  
The policy allows `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable` on **all resources** (`"*"`). These are write actions that can be scoped to specific resource ARNs. Without constraints, an identity with this policy could create resources in any region or account (if cross-account access is possible), leading to uncontrolled resource creation, cost spikes, or data exposure.

**How to fix it:**  
Restrict the `resources` field to the specific ARN patterns of the resources you intend to allow creation of. For example:

```hcl
data "aws_iam_policy_document" "pass" {
  statement {
    effect = "Allow"
    actions = [
      "lambda:CreateFunction",
      "lambda:CreateEventSourceMapping",
    ]
    resources = [
      "arn:aws:lambda:us-east-1:123456789012:function:my-app-*",
    ]
  }
  statement {
    effect = "Allow"
    actions = [
      "dynamodb:CreateTable",
    ]
    resources = [
      "arn:aws:dynamodb:us-east-1:123456789012:table/my-app-*",
    ]
  }
}
```

If you must allow creation of any function/table but only within a specific region or account, use **condition keys** like `aws:RequestedRegion` or `aws:PrincipalAccount` instead of `"*"` in the resource field.

### 2. `aws_iam_policy_document.fail` (lines 60–73)

**Flagged checks:**
- **CKV_AWS_108** – IAM policy should not allow data exfiltration.
- **CKV_AWS_107** – IAM policy should not allow credentials exposure.
- **CKV_AWS_109** – IAM policy should not allow permissions management without constraints.
- **CKV_AWS_110** – IAM policy should not allow privilege escalation.
- **CKV_AWS_356** – IAM policy should not use `"*"` as a resource for restrictable actions.

**Why it’s a problem:**  
The policy allows `s3:GetObject` and `iam:CreateAccessKey` on **all resources** (`"*"`). This is extremely dangerous:
- **Data exfiltration** (`s3:GetObject`): An identity with this policy can read any S3 object in the account, including sensitive data.
- **Credentials exposure / privilege escalation** (`iam:CreateAccessKey`): An identity can create access keys for any IAM user, potentially escalating privileges or exposing long-term credentials.
- **Permissions management without constraints**: `iam:CreateAccessKey` is a permissions management action that should never be granted broadly.

**How to fix it:**  
Break the policy into separate, tightly scoped statements:

```hcl
data "aws_iam_policy_document" "fail" {
  statement {
    effect = "Allow"
    actions = [
      "s3:GetObject",
    ]
    resources = [
      "arn:aws:s3:::my-specific-bucket/*",
    ]
  }
  statement {
    effect = "Allow"
    actions = [
      "iam:CreateAccessKey",
    ]
    resources = [
      "arn:aws:iam::123456789012:user/${aws:username}",   # only for the calling user
    ]
    # Or restrict to a specific user/role ARN:
    # resources = ["arn:aws:iam::123456789012:user/specific-user"]
  }
}
```

For `iam:CreateAccessKey`, the safest approach is to allow it only on the **calling user’s own ARN** using the policy variable `${aws:username}`. If the intent is to allow creating keys for a specific service account, specify that exact user ARN. Never use `"*"`.

---

### Summary of changes needed

- Replace `"*"` in the `resources` field with explicit ARNs or ARN patterns.
- For write actions like `lambda:CreateFunction`, scope to a specific function name pattern and region/account.
- For sensitive actions like `iam:CreateAccessKey`, restrict to the exact user or use condition keys to limit who can be targeted.
- For `s3:GetObject`, restrict to the specific bucket(s) that need to be read.

These changes will satisfy all flagged checks while preserving the intended functionality.
