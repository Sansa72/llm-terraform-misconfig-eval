The scanner flagged several missing security controls on the `aws_s3_bucket` resource named `bucket`. Each finding points to a specific hardening measure that is currently absent. Below is an explanation of what each check requires, why it matters, and how to adjust the Terraform configuration to satisfy all of them while keeping the bucket functional.

### 1. Lifecycle configuration (CKV2_AWS_61)
**What’s missing:** No `lifecycle_rule` block is defined.  
**Why it matters:** Without lifecycle rules, objects may be kept indefinitely, increasing storage costs and the potential blast radius of a data breach. Lifecycle policies can automatically delete old versions or expire objects after a set period, reducing the amount of data at risk.  
**Fix:** Add a `lifecycle_rule` that matches your retention needs. A common safe default is to expire non‑current versions after a number of days.

### 2. Access logging (CKV_AWS_18)
**What’s missing:** No logging configuration is present.  
**Why it matters:** Server access logs provide a record of all requests to the bucket. In the event of a security incident, these logs are essential for forensic analysis and detecting unauthorised access patterns.  
**Fix:** Create a separate logging bucket (or use an existing one) and reference it in a `logging` block. Ensure the target bucket grants the necessary write permissions.

### 3. Event notifications (CKV2_AWS_62)
**What’s missing:** No `event_notification` configuration.  
**Why it matters:** Event notifications allow you to react in near real‑time to object changes (e.g., trigger a Lambda for malware scanning, send alerts on sensitive file uploads). Without them, you lose a layer of proactive monitoring.  
**Fix:** Add an `event_notification` block that sends events to an SNS topic, SQS queue, or Lambda function. You’ll need to create the target resource and grant S3 permission to publish to it.

### 4. Public Access Block (CKV2_AWS_6)
**What’s missing:** No `aws_s3_bucket_public_access_block` resource or inline `public_access_block` configuration.  
**Why it matters:** Without explicit public access block settings, the bucket could accidentally be made public through bucket policies or ACLs. This is a critical guardrail against data leaks.  
**Fix:** Attach a `aws_s3_bucket_public_access_block` resource that blocks all public ACLs and policies, or use the `aws_s3_bucket` resource’s built‑in `public_access_block` argument (available in AWS provider v4+). The safest setting is to block all public access.

### 5. KMS encryption by default (CKV_AWS_145)
**What’s missing:** Default encryption is not configured, or it uses SSE‑S3 instead of SSE‑KMS.  
**Why it matters:** KMS encryption gives you control over the encryption keys, enables key rotation, and provides an audit trail of key usage. SSE‑S3 is less granular and does not offer the same level of accountability.  
**Fix:** Add a `server_side_encryption_configuration` block with `sse_algorithm = "aws:kms"` and specify a KMS key (or use the default `aws/s3` key). Ensure the KMS key policy allows S3 to use it.

### 6. Cross‑region replication (CKV_AWS_144)
**What’s missing:** No replication configuration.  
**Why it matters:** Cross‑region replication (CRR) provides geographic redundancy and can be a requirement for compliance or disaster recovery. It ensures data durability even if an entire AWS region becomes unavailable.  
**Fix:** Create a destination bucket in a different region, an IAM role with replication permissions, and add a `replication_configuration` block. Note that CRR requires versioning to be enabled on both source and destination buckets.

### 7. Versioning (CKV_AWS_21)
**What’s missing:** Versioning is not enabled.  
**Why it matters:** Versioning protects against accidental overwrites and deletions. It is a prerequisite for replication and helps recover from ransomware or user errors.  
**Fix:** Add a `versioning` block with `enabled = true`.

### Example Terraform configuration that satisfies all checks

The snippet below consolidates all required changes. You will need to adapt the bucket names, KMS key, and notification target to your environment.

```hcl
resource "aws_s3_bucket" "bucket" {
  bucket = "module-bucket"   # ensure this is globally unique
}

# Enable versioning
resource "aws_s3_bucket_versioning" "bucket_versioning" {
  bucket = aws_s3_bucket.bucket.id
  versioning_configuration {
    status = "Enabled"
  }
}

# Enable default encryption with KMS
resource "aws_s3_bucket_server_side_encryption_configuration" "bucket_encryption" {
  bucket = aws_s3_bucket.bucket.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = "arn:aws:kms:us-east-1:123456789012:key/your-key-id"  # or use alias
    }
  }
}

# Block all public access
resource "aws_s3_bucket_public_access_block" "bucket_public_access" {
  bucket = aws_s3_bucket.bucket.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# Enable access logging (requires a separate logging bucket)
resource "aws_s3_bucket_logging" "bucket_logging" {
  bucket        = aws_s3_bucket.bucket.id
  target_bucket = "my-logging-bucket"   # replace with your logging bucket
  target_prefix = "log/"
}

# Lifecycle rule (example: expire non‑current versions after 30 days)
resource "aws_s3_bucket_lifecycle_configuration" "bucket_lifecycle" {
  bucket = aws_s3_bucket.bucket.id

  rule {
    id     = "expire-old-versions"
    status = "Enabled"

    noncurrent_version_expiration {
      noncurrent_days = 30
    }
  }
}

# Event notification (example: send to SNS on object creation)
resource "aws_s3_bucket_notification" "bucket_notification" {
  bucket = aws_s3_bucket.bucket.id

  topic {
    topic_arn     = "arn:aws:sns:us-east-1:123456789012:my-topic"  # replace
    events        = ["s3:ObjectCreated:*"]
  }
}

# Cross‑region replication (requires a destination bucket and IAM role)
resource "aws_s3_bucket_replication_configuration" "bucket_replication" {
  # Must have versioning enabled on both buckets
  depends_on = [aws_s3_bucket_versioning.bucket_versioning]

  role   = "arn:aws:iam::123456789012:role/s3-replication-role"  # replace
  bucket = aws_s3_bucket.bucket.id

  rule {
    id     = "replicate-all"
    status = "Enabled"

    destination {
      bucket        = "arn:aws:s3:::my-replication-bucket"  # replace with destination bucket ARN
      storage_class = "STANDARD"
    }
  }
}
```

**Important considerations:**
- **Cross‑region replication** requires a destination bucket in a different region, versioning enabled on both, and an IAM role with appropriate permissions. If replication is not needed for your use case, you may need to suppress the check with an exception; however, the finding expects it to be present.
- **Event notifications** need a valid SNS topic, SQS queue, or Lambda function that S3 can publish to. Create those resources and grant the necessary permissions.
- **KMS key** – if you use a customer‑managed key, ensure its policy allows S3 to use it for encryption/decryption.
- **Logging bucket** must have the correct ACL or bucket policy to accept logs from the source bucket.

Apply these changes to resolve all six findings and bring the bucket into compliance with the security baseline.
