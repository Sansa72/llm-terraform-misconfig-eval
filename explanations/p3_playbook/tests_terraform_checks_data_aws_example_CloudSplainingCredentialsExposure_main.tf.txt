**Remediation Briefing: IAM Policy Document Misconfigurations**

Below are the failing checks in the order reported, with a concise explanation of the issue, its security significance, and the required change. Where multiple checks apply to the same statement, the fixes are interrelated; these interactions are noted at the end.

---

### 1. CKV_AWS_111 on `aws_iam_policy_document.pass` (lines 42–56)
**What is wrong:** The policy grants write actions (`lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, `dynamodb:CreateTable`) on all resources (`"*"`) without any constraints.  
**Why it matters:** Unconstrained write access could allow an attacker or a misused identity to create or modify resources across the entire account, leading to data tampering, resource abuse, or denial of service.  
**Change needed:** Replace the wildcard resource `"*"` with the specific ARNs of the Lambda functions and DynamoDB tables that this policy is intended to manage. If the policy must cover multiple resources, list their exact ARNs or use ARN patterns that include the account ID and region, but avoid a bare `"*"`. Optionally, add condition blocks (e.g., based on tags or source VPC) to further restrict the write access.

---

### 2. CKV_AWS_356 on `aws_iam_policy_document.pass` (lines 42–56)
**What is wrong:** The policy uses `"*"` as the resource for actions (`lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, `dynamodb:CreateTable`) that support resource‑level permissions.  
**Why it matters:** A wildcard resource for restrictable actions violates the principle of least privilege. It grants the ability to perform those actions on any existing or future resource in the account, increasing the blast radius of a compromise.  
**Change needed:** Specify the exact resource ARNs (or ARN patterns with account/region) for the Lambda functions and DynamoDB tables that the policy should affect. This directly aligns with the fix for CKV_AWS_111; once the resource is no longer `"*"`, this check will also pass.

---

### 3. CKV_AWS_108 on `aws_iam_policy_document.fail` (lines 60–73)
**What is wrong:** The policy allows `s3:GetObject` on all resources (`"*"`), enabling unrestricted read access to any S3 object in the account.  
**Why it matters:** This creates a data exfiltration risk. An identity with this policy could read sensitive data from any bucket, including those not intended for that role, and copy it outside the environment.  
**Change needed:** Restrict the `s3:GetObject` action to the specific S3 bucket and object paths that the identity legitimately needs to read. Use a resource ARN like `arn:aws:s3:::my-bucket/*` or a more granular prefix. If the action is not required, remove it entirely.

---

### 4. CKV_AWS_107 on `aws_iam_policy_document.fail` (lines 60–73)
**What is wrong:** The policy includes `iam:CreateAccessKey` on all resources (`"*"`), which can expose long‑term credentials.  
**Why it matters:** Creating access keys for IAM users is a credentials exposure action. An attacker who obtains this permission could generate new keys for privileged users and use them to gain persistent, unauthorized access.  
**Change needed:** Either remove the `iam:CreateAccessKey` action if it is not strictly necessary, or restrict it to the specific IAM user ARNs for which key creation is allowed. Never allow this action on a wildcard resource.

---

### 5. CKV_AWS_356 on `aws_iam_policy_document.fail` (lines 60–73)
**What is wrong:** The policy uses `"*"` as the resource for both `s3:GetObject` and `iam:CreateAccessKey`, which are actions that support resource‑level restrictions.  
**Why it matters:** As with the earlier CKV_AWS_356 finding, a wildcard resource for restrictable actions grants overly broad permissions.  
**Change needed:** Replace `"*"` with the specific resource ARNs for the S3 objects and IAM users that the policy should target. This change is the same as the resource scoping required for the other checks on this policy.

---

### 6. CKV_AWS_109 on `aws_iam_policy_document.fail` (lines 60–73)
**What is wrong:** The policy allows `iam:CreateAccessKey` (a permissions management action) on all resources without constraints.  
**Why it matters:** Unconstrained permissions management can lead to resource exposure and privilege escalation. An identity could create access keys for high‑privilege users, effectively granting itself administrative capabilities.  
**Change needed:** Restrict the `iam:CreateAccessKey` action to specific IAM user ARNs, or remove it if not required. This is the same remediation as for CKV_AWS_107; addressing the wildcard resource and the action’s presence will resolve both.

---

### 7. CKV_AWS_110 on `aws_iam_policy_document.fail` (lines 60–73)
**What is wrong:** The policy allows `iam:CreateAccessKey` on `"*"`, which is a known privilege escalation vector.  
**Why it matters:** An attacker with this permission can create access keys for any IAM user, including those with administrative privileges, and then use those keys to escalate their access.  
**Change needed:** Remove the `iam:CreateAccessKey` action or tightly scope it to the specific IAM users that require key creation. This single change will also satisfy CKV_AWS_107, CKV_AWS_109, and the resource‑restriction requirement of CKV_AWS_356 for that action.

---

### Interactions Between Fixes
- **`aws_iam_policy_document.pass`:** Both CKV_AWS_111 and CKV_AWS_356 are triggered by the same wildcard resource. Replacing `"*"` with specific resource ARNs (and optionally adding conditions) will clear both checks simultaneously.  
- **`aws_iam_policy_document.fail`:** All five checks (CKV_AWS_108, CKV_AWS_107, CKV_AWS_356, CKV_AWS_109, CKV_AWS_110) stem from the single statement that combines `s3:GetObject` and `iam:CreateAccessKey` on `"*"`. Splitting the statement into two—one for S3 and one for IAM—and scoping each to its appropriate resources will resolve every check. If `iam:CreateAccessKey` is removed entirely, the IAM‑related checks (107, 109, 110) and the wildcard issue for that action are eliminated; the S3 statement still needs its resource narrowed to pass CKV_AWS_108 and CKV_AWS_356.

No other resources in the supplied file are affected. Implement the changes as described to bring both policy documents into compliance.
