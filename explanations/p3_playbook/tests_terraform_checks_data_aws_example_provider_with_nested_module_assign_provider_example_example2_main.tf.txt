**Remediation briefing: aws_s3_bucket.bucket**

All findings apply to the same resource, `aws_s3_bucket "bucket"` (lines 1–3). The bucket currently has no security or lifecycle features configured. The fixes are independent except where noted.

---

### 1. CKV2_AWS_61 – Ensure that an S3 bucket has a lifecycle configuration  
**Resource:** `aws_s3_bucket.bucket`  
**What’s wrong:** No lifecycle rules are defined for the bucket.  
**Why it matters:** Without lifecycle rules, objects accumulate indefinitely, increasing storage costs and potentially retaining stale or sensitive data longer than necessary. Lifecycle policies can automatically transition objects to cheaper storage classes or expire them after a defined period, reducing risk and cost.  
**Change needed:** Add an `aws_s3_bucket_lifecycle_configuration` resource associated with this bucket. Define at least one rule that either expires objects or transitions them to another storage class (e.g., after 90 days). The rule should apply to the whole bucket or a filtered prefix.

---

### 2. CKV_AWS_18 – Ensure the S3 bucket has access logging enabled  
**Resource:** `aws_s3_bucket.bucket`  
**What’s wrong:** Server access logging is not enabled.  
**Why it matters:** Access logs provide an audit trail of all requests to the bucket, which is essential for security investigations, compliance, and detecting unauthorised access.  
**Change needed:** Create an `aws_s3_bucket_logging` resource that references this bucket. You must also specify a target bucket where the logs will be delivered. The target bucket must already exist and have appropriate permissions (ACL or bucket policy) to allow the source bucket to write logs. If no suitable target bucket exists, create one first.

---

### 3. CKV2_AWS_62 – Ensure S3 buckets should have event notifications enabled  
**Resource:** `aws_s3_bucket.bucket`  
**What’s wrong:** No event notifications are configured.  
**Why it matters:** Event notifications allow real-time alerting or automated response to bucket activity (e.g., object creation, deletion). This is critical for security monitoring, data processing pipelines, and compliance controls.  
**Change needed:** Add an `aws_s3_bucket_notification` resource linked to this bucket. Define at least one notification configuration (e.g., for `s3:ObjectCreated:*` events) and specify a destination such as an SNS topic, SQS queue, or Lambda function. The destination must already exist and have a resource-based policy allowing S3 to publish to it.

---

### 4. CKV2_AWS_6 – Ensure that S3 bucket has a Public Access block  
**Resource:** `aws_s3_bucket.bucket`  
**What’s wrong:** No public access block configuration is attached.  
**Why it matters:** Without a public access block, the bucket could inadvertently be made public through ACLs or policies, exposing data to the internet. The block provides a hard override that prevents any public access regardless of other settings.  
**Change needed:** Add an `aws_s3_bucket_public_access_block` resource for this bucket. Set all four block flags (`block_public_acls`, `block_public_policy`, `ignore_public_acls`, `restrict_public_buckets`) to `true` to enforce the strictest protection.

---

### 5. CKV_AWS_145 – Ensure that S3 buckets are encrypted with KMS by default  
**Resource:** `aws_s3_bucket.bucket`  
**What’s wrong:** Default encryption is not configured to use AWS KMS (SSE-KMS).  
**Why it matters:** Default encryption ensures that all objects stored in the bucket are encrypted at rest. Using KMS provides greater control over key rotation, access auditing, and separation of duties compared to SSE-S3.  
**Change needed:** Add an `aws_s3_bucket_server_side_encryption_configuration` resource. In the rule, set `apply_server_side_encryption_by_default.sse_algorithm` to `aws:kms` and optionally specify a KMS key ARN (otherwise the AWS-managed `aws/s3` key is used). If you use a customer-managed KMS key, ensure the bucket’s principal has `kms:GenerateDataKey` and `kms:Decrypt` permissions on that key.

---

### 6. CKV_AWS_144 – Ensure that S3 bucket has cross-region replication enabled  
**Resource:** `aws_s3_bucket.bucket`  
**What’s wrong:** No replication configuration is present.  
**Why it matters:** Cross-region replication (CRR) provides geographic redundancy, helping meet disaster recovery and compliance requirements. It ensures data durability by automatically copying objects to a bucket in a different AWS region.  
**Change needed:** Add an `aws_s3_bucket_replication_configuration` resource. This requires:
- A destination bucket in a different region (must already exist).
- An IAM role with permissions to replicate objects.
- **Versioning must be enabled on both source and destination buckets** (see CKV_AWS_21 below).  
The replication rule should specify the destination bucket and the IAM role. If you also enable delete marker replication, be aware of the cost and retention implications.

---

### 7. CKV_AWS_21 – Ensure all data stored in the S3 bucket have versioning enabled  
**Resource:** `aws_s3_bucket.bucket`  
**What’s wrong:** Versioning is not enabled.  
**Why it matters:** Versioning protects against accidental overwrites and deletions by preserving every version of an object. It is a prerequisite for replication and can be combined with lifecycle rules to manage old versions.  
**Change needed:** Add an `aws_s3_bucket_versioning` resource for this bucket and set `versioning_configuration.status` to `Enabled`. Once enabled, versioning cannot be fully disabled (only suspended), so plan accordingly.

---

### Interactions between fixes
- **Versioning (CKV_AWS_21) is a prerequisite for replication (CKV_AWS_144).** You must enable versioning on the source bucket before configuring replication; otherwise the replication configuration will fail.  
- **Lifecycle (CKV2_AWS_61) can be used to manage versioned objects** – for example, expiring non-current versions after a certain number of days. This is recommended once versioning is enabled to control storage growth.  
- **Access logging (CKV_AWS_18) and event notifications (CKV2_AWS_62) both require separate destination resources** (a log bucket and a notification target, respectively). These can be created independently, but ensure the necessary permissions are in place.  
- All other fixes (public access block, KMS encryption) are independent and can be applied in any order.
