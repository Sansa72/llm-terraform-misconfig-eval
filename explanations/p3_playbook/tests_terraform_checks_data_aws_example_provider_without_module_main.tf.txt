## Remediation Briefing: S3 Security Misconfigurations

Below is a per‑finding breakdown of the issues flagged by the scanner, why they matter, and what needs to change. Both buckets (`aws_s3_bucket.bucket` and `aws_s3_bucket.bucket_2`) are affected identically. The fixes are described in prose; no complete Terraform blocks are provided.

---

### 1. CKV2_AWS_61 – S3 bucket lifecycle configuration
**Resource:** `aws_s3_bucket.bucket` (line 10)  
**What’s wrong:** No lifecycle configuration is attached to the bucket.  
**Why it matters:** Without lifecycle rules, objects can accumulate indefinitely, increasing storage costs and making it harder to manage data retention, compliance, and deletion of stale data.  
**Change needed:** Add an `aws_s3_bucket_lifecycle_configuration` resource that references this bucket. Define at least one rule (e.g., transition objects to a cheaper storage class after a number of days, or expire old versions). The rule must be appropriate for the bucket’s data retention requirements.

**Resource:** `aws_s3_bucket.bucket_2` (line 15)  
**What’s wrong:** Same as above – no lifecycle configuration.  
**Why it matters:** Same cost and data management concerns.  
**Change needed:** Create a separate `aws_s3_bucket_lifecycle_configuration` resource for `bucket_2` with a suitable lifecycle rule.

---

### 2. CKV_AWS_18 – S3 bucket access logging
**Resource:** `aws_s3_bucket.bucket` (line 10)  
**What’s wrong:** Server access logging is not enabled on the bucket.  
**Why it matters:** Without access logs, you lose visibility into who is accessing the bucket and what actions they perform, hindering security investigations and compliance audits.  
**Change needed:** Provision a target bucket (or use an existing one) to store the logs, then attach an `aws_s3_bucket_logging` resource to `aws_s3_bucket.bucket` that points to that target bucket. Ensure the target bucket’s policy allows the source bucket to write logs.

**Resource:** `aws_s3_bucket.bucket_2` (line 15)  
**What’s wrong:** Same – no access logging.  
**Why it matters:** Same loss of audit trail.  
**Change needed:** Similarly, create a logging configuration for `bucket_2` using a target bucket (can be the same log‑destination bucket as above, with appropriate prefix separation, or a separate one).

---

### 3. CKV2_AWS_62 – S3 bucket event notifications
**Resource:** `aws_s3_bucket.bucket` (line 10)  
**What’s wrong:** No event notification configuration is defined for the bucket.  
**Why it matters:** Without event notifications, you cannot automatically trigger workflows (e.g., malware scanning, data processing, or alerting) when objects are created or modified, reducing operational responsiveness and security monitoring.  
**Change needed:** Add an `aws_s3_bucket_notification` resource that references this bucket. Define at least one notification destination (SNS topic, SQS queue, or Lambda function) and specify the events to monitor (e.g., `s3:ObjectCreated:*`). The destination resource must already exist or be created alongside.

**Resource:** `aws_s3_bucket.bucket_2` (line 15)  
**What’s wrong:** Same – no event notifications.  
**Why it matters:** Same lack of automated event‑driven security.  
**Change needed:** Create a separate `aws_s3_bucket_notification` for `bucket_2`, pointing to an appropriate destination.

---

### 4. CKV2_AWS_6 – S3 bucket Public Access Block
**Resource:** `aws_s3_bucket.bucket` (line 10)  
**What’s wrong:** No public access block configuration is attached to the bucket.  
**Why it matters:** Without explicit block settings, the bucket could inadvertently be made public through bucket policies or ACLs, leading to data exposure.  
**Change needed:** Add an `aws_s3_bucket_public_access_block` resource that references this bucket. Set all four block options (`block_public_acls`, `block_public_policy`, `ignore_public_acls`, `restrict_public_buckets`) to `true` to enforce a deny‑all‑public‑access posture.

**Resource:** `aws_s3_bucket.bucket_2` (line 15)  
**What’s wrong:** Same – no public access block.  
**Why it matters:** Same risk of unintended public exposure.  
**Change needed:** Create a corresponding `aws_s3_bucket_public_access_block` for `bucket_2` with all four blocks enabled.

---

### 5. CKV_AWS_145 – Default encryption with KMS
**Resource:** `aws_s3_bucket.bucket` (line 10)  
**What’s wrong:** The bucket does not enforce default encryption using a KMS key.  
**Why it matters:** Without default encryption, objects may be stored unencrypted, violating data protection policies and regulatory requirements. KMS provides centralized key management and access control.  
**Change needed:** Add an `aws_s3_bucket_server_side_encryption_configuration` resource for this bucket. In the rule, set `apply_server_side_encryption_by_default.sse_algorithm` to `aws:kms` and optionally specify a KMS key ARN. If you omit the key, AWS will use the default `aws/s3` KMS key.

**Resource:** `aws_s3_bucket.bucket_2` (line 15)  
**What’s wrong:** Same – no default KMS encryption.  
**Why it matters:** Same encryption gap.  
**Change needed:** Create a separate `aws_s3_bucket_server_side_encryption_configuration` for `bucket_2` with the same KMS settings.

---

### 6. CKV_AWS_144 – Cross‑region replication
**Resource:** `aws_s3_bucket.bucket` (line 10)  
**What’s wrong:** Cross‑region replication (CRR) is not enabled.  
**Why it matters:** CRR provides geographic redundancy and can help meet compliance requirements for data durability and disaster recovery.  
**Change needed:**  
- First, **versioning must be enabled** on both the source bucket and the destination bucket (see CKV_AWS_21 below).  
- Create a destination bucket in a different region (e.g., `us-east-1`).  
- Add an `aws_s3_bucket_replication_configuration` resource to the source bucket, referencing the destination bucket and an IAM role that grants S3 permission to replicate objects.  
- The destination bucket must also have a replication‑supporting policy.  
- **Interaction:** This fix depends on enabling versioning (CKV_AWS_21) for both buckets. The destination bucket is not present in the current file; you will need to create it.

**Resource:** `aws_s3_bucket.bucket_2` (line 15)  
**What’s wrong:** Same – no CRR.  
**Why it matters:** Same need for geographic redundancy.  
**Change needed:** Follow the same steps as above for `bucket_2`, using a destination bucket in a different region (can be the same destination bucket as for `bucket`, with a separate replication rule, or a dedicated one). Again, versioning must be enabled first.

---

### 7. CKV_AWS_21 – S3 bucket versioning
**Resource:** `aws_s3_bucket.bucket` (line 10)  
**What’s wrong:** Versioning is not enabled on the bucket.  
**Why it matters:** Without versioning, overwritten or deleted objects cannot be recovered, increasing the risk of accidental or malicious data loss. Versioning is also a prerequisite for replication and can be used with lifecycle policies to manage non‑current versions.  
**Change needed:** Add an `aws_s3_bucket_versioning` resource that references this bucket and sets `versioning_configuration.status` to `Enabled`.  
- **Interaction:** Enabling versioning is required before you can configure cross‑region replication (CKV_AWS_144). If you plan to implement replication, apply the versioning fix first.

**Resource:** `aws_s3_bucket.bucket_2` (line 15)  
**What’s wrong:** Same – versioning is not enabled.  
**Why it matters:** Same data protection and replication prerequisite.  
**Change needed:** Create a corresponding `aws_s3_bucket_versioning` resource for `bucket_2` with `status = "Enabled"`. This must be done before any replication configuration for this bucket.

---

### Additional note on provider configuration
The `aws_s3_bucket.bucket` resource uses `provider = aws.usw1`, but that provider block has an empty `region` string. This will likely cause an error at plan/apply time. While not directly flagged by the scanner, you should correct the region (e.g., `region = "us-west-1"`) to ensure the bucket is created in the intended region and that cross‑region replication can be set up correctly.
