**Remediation briefing for CloudFront distribution security findings**

Below are the failing checks in the order reported by the scanner. For each, the resource, the problem, its importance, and the required change are described. Where fixes interact, those interactions are noted.

---

1. **CKV_AWS_216 on `aws_cloudfront_distribution.pass`**  
   *What is wrong:* The distribution is disabled (`enabled = false`).  
   *Why it matters:* A disabled distribution cannot serve content, but more importantly, leaving it disabled may mask misconfigurations that would otherwise be detected. Production distributions must be explicitly enabled.  
   *Change needed:* Set `enabled = true` in the resource block.

2. **CKV_AWS_86 on `aws_cloudfront_distribution.pass`**  
   *What is wrong:* Access logging is not configured.  
   *Why it matters:* Without access logs, you lose visibility into requests, which hinders security investigations, operational monitoring, and compliance.  
   *Change needed:* Add a `logging_config` block inside the resource. Provide an S3 bucket (with appropriate permissions) and an optional prefix. For example:
   ```
   logging_config {
     bucket = "<log-bucket-name>.s3.amazonaws.com"
     prefix = "cloudfront/pass/"
   }
   ```

3. **CKV_AWS_174 on `aws_cloudfront_distribution.pass`**  
   *What is wrong:* The viewer certificate does not enforce TLS v1.2.  
   *Why it matters:* Older TLS versions have known vulnerabilities; requiring TLS v1.2 or higher protects data in transit.  
   *Change needed:* In the `viewer_certificate` block, set `minimum_protocol_version = "TLSv1.2_2021"` (or a similar TLSv1.2 variant). If you later switch to a custom certificate (see CKV2_AWS_42), this same setting will satisfy the check.

4. **CKV_AWS_68 on `aws_cloudfront_distribution.pass`**  
   *What is wrong:* No WAF web ACL is associated with the distribution.  
   *Why it matters:* A WAF helps protect against common web exploits like SQL injection and cross‑site scripting. Without it, the distribution is exposed to application‑layer attacks.  
   *Change needed:* Create an `aws_wafv2_web_acl` resource (or use an existing one) and reference its ARN in the distribution’s `web_acl_id` argument. This also enables the fix for CKV2_AWS_47 (Log4j rule) – see item 30.

5. **CKV_AWS_305 on `aws_cloudfront_distribution.pass`**  
   *What is wrong:* No default root object is defined.  
   *Why it matters:* Without a default root object, requests to the distribution’s root URL (e.g., `https://example.com/`) return an error instead of a default page, degrading user experience and potentially leaking information.  
   *Change needed:* Set `default_root_object = "index.html"` (or another appropriate object) in the resource.

6. **CKV_AWS_86 on `aws_cloudfront_distribution.fail`**  
   *What is wrong:* Access logging is not configured.  
   *Why it matters:* Same as item 2 – no request visibility.  
   *Change needed:* Add a `logging_config` block with a valid S3 bucket and optional prefix.

7. **CKV_AWS_174 on `aws_cloudfront_distribution.fail`**  
   *What is wrong:* The viewer certificate uses the default CloudFront certificate and does not enforce TLS v1.2.  
   *Why it matters:* Same as item 3 – weak transport security.  
   *Change needed:* In the existing `viewer_certificate` block, add `minimum_protocol_version = "TLSv1.2_2021"`. If you later replace the default certificate with a custom one (CKV2_AWS_42), keep this setting.

8. **CKV_AWS_68 on `aws_cloudfront_distribution.fail`**  
   *What is wrong:* No WAF web ACL is associated.  
   *Why it matters:* Same as item 4 – missing application‑layer protection.  
   *Change needed:* Attach a WAFv2 web ACL via `web_acl_id`. This will also be the foundation for the Log4j rule check (CKV2_AWS_47, item 31).

9. **CKV_AWS_310 on `aws_cloudfront_distribution.fail`**  
   *What is wrong:* Origin failover is not configured. The distribution has only a single origin and no origin group.  
   *Why it matters:* Without origin failover, an origin outage causes a complete service disruption. Failover provides high availability.  
   *Change needed:* Add an `origin_group` block with at least two members and a `failover_criteria` block (e.g., status codes 403, 404, 500, 502). Then point the cache behavior’s `target_origin_id` to the origin group ID. This is similar to the pattern already present in the `pass` resource.

10. **CKV_AWS_216 on `aws_cloudfront_distribution.fail2`**  
    *What is wrong:* The distribution is disabled (`enabled = false`).  
    *Why it matters:* Same as item 1.  
    *Change needed:* Set `enabled = true`.

30. **CKV2_AWS_47 on `aws_cloudfront_distribution.pass`**

This must be done in the same web ACL that is attached to the distribution.

**Key interactions to note:**

- **WAF attachment (CKV_AWS_68) and Log4j rule (CKV2_AWS_47):** The WAFv2 web ACL you create to satisfy CKV_AWS_68 must also contain the `AWSManagedRulesKnownBadInputsRuleSet` managed rule group to pass CKV2_AWS_47. Plan a single web ACL resource per distribution that includes this rule group, then reference it in `web_acl_id`.
- **Custom SSL certificate (CKV2_AWS_42) and TLS v1.2 (CKV_AWS_174):** When you switch from the default certificate to a custom ACM certificate, you must set `minimum_protocol_version = "TLSv1.2_2021"` (or a similar TLSv1.2 value) in the `viewer_certificate` block. This single change satisfies both checks.
- **Origin failover (CKV_AWS_310) and origin group structure:** The `origin_group` block requires both `failover_criteria` and at least two `member` blocks. The `fail` resource lacks the entire group; `fail2` has members but no criteria; `fail3` has criteria but no members. Each must be completed according to its missing piece.
