The scanner raised six distinct findings across two IAM policy documents: `aws_iam_policy_document.pass` and `aws_iam_policy_document.fail`. The `allowed_action` and `deny` documents are not flagged and require no changes. Below I explain each finding, why it matters, and what must change to resolve it.

---

### `aws_iam_policy_document.pass` (lines 42–56)

**1. CKV_AWS_111 – Write access without constraints**  
The policy allows `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable`. All three are **write** actions (they create resources). The statement uses `resources = ["*"]` and has no conditions. This means the policy grants unrestricted ability to create Lambda functions, event source mappings, and DynamoDB tables in any account region, with any configuration. An attacker or a compromised workload could use this to deploy malicious resources, consume capacity, or incur costs.

*Fix:* Either replace `"*"` with specific resource ARNs (e.g., `arn:aws:lambda:us-east-1:123456789012:function:*` for a particular account/region) **or** add a condition that constrains the write access. A common constraint is `"aws:RequestedRegion"` to limit creation to a single region, or `"aws:ResourceTag"` to enforce tagging. Ideally, do both: scope the resource ARN and add a condition.

**2. CKV_AWS_356 – Wildcard resource for restrictable actions**  
The same three actions (`lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, `dynamodb:CreateTable`) are “restrictable” – they can be scoped to specific resources. Using `"*"` as the resource violates the principle of least privilege and makes the policy overly broad.

*Fix:* Specify the exact resource ARNs that the identity should be allowed to create. For example, if this policy is attached to a role that only needs to create functions in a particular account and region, set `resources` to `["arn:aws:lambda:us-east-1:123456789012:function:*"]`. For DynamoDB, use the table ARN pattern. This change will also help satisfy CKV_AWS_111.

### `aws_iam_policy_document.fail` (lines 60–73)

**3. CKV_AWS_108 – Data exfiltration**  
The action `s3:GetObject` with `resources = ["*"]` allows reading any object from any S3 bucket in the account. This is a classic data exfiltration risk: a compromised identity could download sensitive data from any bucket.

*Fix:* Restrict the resource to the specific bucket(s) and object prefix(es) that the identity genuinely needs to read. For example, `"arn:aws:s3:::my-bucket/specific-path/*"`. If the action must be broad, add a condition such as `"s3:ResourceTag"` or a `"StringEquals"` on `"s3:prefix"` to limit scope.

**4. CKV_AWS_107 – Credentials exposure**  
The action `iam:CreateAccessKey` with `resources = ["*"]` allows creating access keys for **any** IAM user in the account. This is a direct credentials exposure risk: an attacker could generate long-term access keys for a privileged user and then use those keys outside the intended workflow.

*Fix:* Restrict the resource to the specific IAM user ARN(s) that require this permission. For example, `"arn:aws:iam::123456789012:user/username"`. If the policy is meant for a user to manage their own access keys, use `"${aws:username}"` as the resource and ensure the policy is attached only to that user. Alternatively, remove `iam:CreateAccessKey` entirely if it is not needed.

**5. CKV_AWS_356 – Wildcard resource for restrictable actions**  
Both `s3:GetObject` and `iam:CreateAccessKey` are restrictable actions, yet the policy uses `"*"` as the resource. This is the same issue as finding #2, now applied to the `fail` document.

*Fix:* As described above, replace `"*"` with specific resource ARNs for each action. If the two actions require different resources, split them into separate statements so each can have its own resource list.

**6. CKV_AWS_109 – Permissions management / resource exposure without constraints**  
`iam:CreateAccessKey` is considered a permissions‑management action because it can expose long‑term credentials, effectively granting access to the user’s permissions. Allowing it on `"*"` without any condition means the policy can expose any user’s credentials.

*Fix:* Restrict the resource to the specific user ARN(s) that need this capability, and add a condition if possible (e.g., `"Bool": {"aws:MultiFactorAuthPresent": "true"}` to require MFA). This directly overlaps with the fix for CKV_AWS_107.

**7. CKV_AWS_110 – Privilege escalation**  
`iam:CreateAccessKey` is also a known privilege‑escalation vector. If an identity can create access keys for a more privileged user, it can then assume that user’s permissions. The wildcard resource makes this trivially exploitable.

*Fix:* The same resource restriction and condition additions that resolve CKV_AWS_107 and CKV_AWS_109 will also resolve this finding. Ensure the policy cannot be used to create keys for any user other than the intended, low‑privilege one.

---

### Summary of required changes

- **For `aws_iam_policy_document.pass`:** Replace `resources = ["*"]` with specific ARN patterns for the Lambda and DynamoDB resources, and add a condition (e.g., `aws:RequestedRegion`) to constrain the write actions.
- **For `aws_iam_policy_document.fail`:** Split the statement so that `s3:GetObject` and `iam:CreateAccessKey` each have their own resource list. Restrict `s3:GetObject` to the exact bucket/prefix needed. Restrict `iam:CreateAccessKey` to the specific IAM user ARN(s) that require it, and consider adding an MFA condition. If `iam:CreateAccessKey` is not strictly necessary, remove it entirely.

All fixes follow the same principle: never use `"*"` as a resource for actions that can be scoped, and always pair broad or sensitive actions with conditions that limit their effective scope.
