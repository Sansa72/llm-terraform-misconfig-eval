The scanner flagged two IAM policy documents in your Terraform file: the one named `pass` (lines 42–56) and the one named `fail` (lines 60–73). Both grant overly broad permissions that violate AWS security best practices. Below I’ll break down each finding, why it’s a problem in your specific configuration, and how to fix it.

---

## Policy `pass` (lines 42–56)

```hcl
data "aws_iam_policy_document" "pass" {
  statement {
    effect    = "Allow"
    actions   = ["lambda:CreateFunction", "lambda:CreateEventSourceMapping", "dynamodb:CreateTable"]
    resources = ["*"]
  }
}
```

### Findings

- **CKV_AWS_111 – Ensure IAM policies does not allow write access without constraints**  
  This policy allows three write actions (`CreateFunction`, `CreateEventSourceMapping`, `CreateTable`) on **all resources** (`"*"`) with no conditions. That means any principal attached to this policy can create Lambda functions, event source mappings, and DynamoDB tables anywhere in the account, without restrictions like source IP, MFA, or tags. This is a classic unconstrained write access risk.

- **CKV_AWS_356 – Ensure no IAM policies documents allow "*" as a statement's resource for restrictable actions**  
  All three actions are resource‑level permissions (you can scope them to specific function names, table names, etc.). Using `"*"` as the resource grants these write capabilities over every existing and future resource of that type in the account. The rule requires that you specify the actual resources (or at least a constrained ARN pattern) instead of a wildcard.

**Remediation:**  
- Replace `resources = ["*"]` with the ARNs of the specific Lambda functions, event source mappings, and DynamoDB tables that need to be created. For example:  
  `resources = ["arn:aws:lambda:us-east-1:123456789012:function:my-function"]`  
- If the policy must apply to multiple resources, use a constrained wildcard like `arn:aws:lambda:us-east-1:123456789012:function:${var.prefix}-*`.  
- Add a condition (e.g., `aws:RequestedRegion`, `aws:SourceIp`, or `aws:PrincipalTag`) to limit when the write actions can be performed.

## Policy `fail` (lines 60–73)

```hcl
data "aws_iam_policy_document" "fail" {
  statement {
    effect    = "Allow"
    actions   = ["s3:GetObject", "iam:CreateAccessKey"]
    resources = ["*"]
  }
}
```

This policy is even more dangerous because it combines two highly sensitive actions with a wildcard resource.

### Findings

- **CKV_AWS_108 – Ensure IAM policies does not allow data exfiltration**  
  `s3:GetObject` allows reading objects from S3. With `resources = ["*"]`, it grants read access to **every object in every S3 bucket** in the account. This is a classic data exfiltration vector – an attacker or compromised workload could download sensitive data from any bucket.

- **CKV_AWS_107 – Ensure IAM policies does not allow credentials exposure**  
  `iam:CreateAccessKey` allows creating a new access key for an IAM user. With a wildcard resource, it can be used to create keys for **any IAM user**, including privileged ones. The newly created key could then be used outside the normal credential lifecycle, leading to credential exposure and persistent access.

- **CKV_AWS_109 – Ensure IAM policies does not allow permissions management / resource exposure without constraints**  
  `iam:CreateAccessKey` is a permissions management action because it creates credentials that directly grant permissions. Allowing it on `"*"` without conditions means you can manage the permissions of any user (by creating a key for them) without any guardrails.

- **CKV_AWS_110 – Ensure IAM policies does not allow privilege escalation**  
  `iam:CreateAccessKey` is a well‑known privilege escalation method. An attacker with this permission can create an access key for a higher‑privileged user (e.g., an admin) and then use that key to escalate their own privileges. The wildcard resource makes this trivially exploitable.

- **CKV_AWS_356 – (again) Wildcard resource for restrictable actions**  
  Both `s3:GetObject` and `iam:CreateAccessKey` are resource‑level actions. `s3:GetObject` can be scoped to specific buckets/objects; `iam:CreateAccessKey` can be scoped to specific user ARNs. Using `"*"` violates the principle of least privilege.

**Remediation:**  
- **For `s3:GetObject`:** Restrict the resource to the exact bucket(s) and object prefix(es) that need to be read. For example:  
  `resources = ["arn:aws:s3:::my-app-bucket", "arn:aws:s3:::my-app-bucket/*"]`  
  If the action is only needed for a specific application, never use `"*"`.  
- **For `iam:CreateAccessKey`:** This action is extremely sensitive and should rarely be allowed. If it is absolutely required, restrict the resource to the specific IAM user(s) that need to have keys created programmatically, e.g.:  
  `resources = ["arn:aws:iam::123456789012:user/${var.service_user_name}"]`  
  Add strong conditions such as `aws:MultiFactorAuthPresent: true` or `aws:SourceIp` to limit who can perform the action and from where.  
- **General:** Split the two actions into separate statements if they require different resource constraints or conditions. Never combine data‑access and credential‑management actions in a single broad statement.

## Why the other policies are not flagged

- **`deny`** – This is a `Deny` statement with conditions, so it’s not granting any permissions; it’s restricting them. The scanner rules focus on `Allow` statements.

The fixes above will bring your policies in line with the principle of least privilege and resolve all flagged issues.
