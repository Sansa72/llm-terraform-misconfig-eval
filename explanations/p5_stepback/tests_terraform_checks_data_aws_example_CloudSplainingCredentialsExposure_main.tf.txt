### Policy `data.aws_iam_policy_document.pass` (lines 42–56)

**Findings:**
- CKV_AWS_111: Ensure IAM policies do not allow write access without constraints
- CKV_AWS_356: Ensure no IAM policies documents allow `"*"` as a statement’s resource for restrictable actions

**Principle (CKV_AWS_111):**  
Write actions (create, modify, delete) should be scoped to the minimum set of resources required and, where possible, constrained by conditions such as tags, source IP, or VPC endpoints. Unrestricted write access increases the blast radius of a compromised identity and can lead to unauthorized resource creation or modification.

**Application:**  
The statement allows `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable` on `"*"` with no conditions. These are all write actions that create resources. Without any condition, an identity with this policy can create Lambda functions, event source mappings, and DynamoDB tables in any region of the account, potentially incurring cost, interfering with existing workloads, or being used for malicious purposes. The policy must be constrained—for example, by requiring specific resource name patterns, tags, or a source VPC/region condition.

**Principle (CKV_AWS_356):**  
For actions that support resource‑level permissions (i.e., you can specify an ARN instead of `*`), using `"*"` as the resource grants access to all resources of that type, violating least privilege. Even for “create” actions that often require `"*"` because the resource does not yet exist, the policy should be restricted with conditions to limit the scope of creation.

**Application:**  
The actions `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable` are all flagged as restrictable. The policy uses `"*"` as the resource without any conditions. While creation actions may technically require `"*"` as the resource ARN, the lack of any condition (e.g., `aws:RequestedRegion`, `aws:ResourceTag`, or `lambda:FunctionArn` condition keys) means the policy is effectively unrestricted. The fix is to add conditions that limit where and under what circumstances these resources can be created, or to split the policy and restrict the resource ARN for actions that do support resource‑level scoping.

### Policy `data.aws_iam_policy_document.fail` (lines 60–73)

**Findings:**
- CKV_AWS_108: Ensure IAM policies do not allow data exfiltration
- CKV_AWS_107: Ensure IAM policies do not allow credentials exposure
- CKV_AWS_356: Ensure no IAM policies documents allow `"*"` as a statement’s resource for restrictable actions
- CKV_AWS_109: Ensure IAM policies do not allow permissions management / resource exposure without constraints
- CKV_AWS_110: Ensure IAM policies do not allow privilege escalation

**Principle (CKV_AWS_108 – data exfiltration):**  
Policies must not grant broad read access to data stores (e.g., S3, DynamoDB, RDS) because an identity with such access can copy sensitive data to an external location. The resource should be scoped to the minimum necessary buckets/objects, and conditions (e.g., source VPC, MFA) should be applied.

**Application:**  
The statement allows `s3:GetObject` on `"*"`. This permits reading any object from any S3 bucket in the account, enabling wholesale data exfiltration. The resource must be restricted to the specific bucket(s) and object prefix(es) that the identity legitimately needs to read.

**Principle (CKV_AWS_107 – credentials exposure):**  
Actions that create or manage long‑term credentials (e.g., `iam:CreateAccessKey`, `iam:UpdateAccessKey`) must be tightly controlled. Allowing these on `"*"` lets an identity generate access keys for any IAM user, including highly privileged ones, leading to credential leakage and account takeover.

**Application:**  
The statement allows `iam:CreateAccessKey` on `"*"`. This means the identity can create a new access key for any IAM user in the account. An attacker who obtains this permission can create keys for an admin user and then use those keys to escalate access. The resource must be restricted to specific IAM users (or roles) that the identity is authorized to manage, and ideally further constrained with conditions (e.g., MFA required).

**Principle (CKV_AWS_356 – wildcard resource for restrictable actions):**  
Both `s3:GetObject` and `iam:CreateAccessKey` are actions that support resource‑level permissions. Using `"*"` as the resource grants access to all objects/users, violating least privilege.

**Application:**  
The policy uses `"*"` for both actions. The resource must be narrowed to the specific S3 bucket/object ARN and the specific IAM user ARN(s) that the identity needs to manage.

**Principle (CKV_AWS_109 – permissions management/resource exposure):**  
Actions that create, modify, or delete IAM resources (like `iam:CreateAccessKey`) are considered permissions management. Allowing them without resource or condition constraints can lead to unauthorized privilege grants or resource exposure.

**Application:**  
The `iam:CreateAccessKey` action is a permissions management action. By allowing it on `"*"`, the policy grants the ability to create access keys for any user, effectively exposing the entire IAM user base to credential compromise. The resource must be scoped to specific user ARNs, and conditions should be added.

**Principle (CKV_AWS_110 – privilege escalation):**  
Policies must not allow actions that can be chained to gain higher privileges than intended. `iam:CreateAccessKey` is a known escalation vector because an attacker with this permission can create a key for a more privileged user and then assume that user’s permissions.

**Application:**  
The combination of `s3:GetObject` and `iam:CreateAccessKey` on `"*"` is particularly dangerous. An identity with this policy could exfiltrate data from any S3 bucket and then create access keys for any IAM user, potentially escalating to full administrative access. The `iam:CreateAccessKey` action must be removed or severely restricted to a specific, low‑privilege user and protected by conditions.

### Required changes

1. **For the `pass` policy:**  
   - Add conditions to the statement (e.g., `"StringEquals": {"aws:RequestedRegion": "us-east-1"}` or `"Null": {"aws:ResourceTag/Environment": "false"}`) to limit where and under what circumstances resources can be created.  
   - If any of the actions can be scoped to specific resource ARNs (e.g., `dynamodb:CreateTable` supports specifying a table ARN pattern), replace `"*"` with the appropriate ARN.

2. **For the `fail` policy:**  
   - Replace `"*"` in the `s3:GetObject` resource with the ARN of the specific bucket and object prefix that the identity needs to access (e.g., `arn:aws:s3:::my-bucket/my-prefix/*`).  
   - Remove `iam:CreateAccessKey` entirely unless absolutely necessary. If it is required, restrict the resource to the exact IAM user ARN(s) that the identity is allowed to manage, and add a condition requiring MFA or a specific source IP.  
   - Consider whether these two permissions belong in the same policy at all; separating them reduces the blast radius.

These changes will align the policies with least privilege and eliminate the flagged risks.
