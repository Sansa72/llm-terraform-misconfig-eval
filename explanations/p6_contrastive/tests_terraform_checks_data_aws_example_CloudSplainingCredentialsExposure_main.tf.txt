**CKV_AWS_111 – IAM policy allows write access without constraints (policy `pass`)**

- **Current behavior:** The policy grants `Allow` for the write actions `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable` on **all resources (`"*"`)** without any condition.
- **Satisfying configuration:** The policy would either restrict the `resources` field to specific ARNs (e.g., `arn:aws:lambda:us-east-1:123456789012:function:my-function`) or add a `condition` block that limits when the write actions can be performed (e.g., only from a particular VPC endpoint, source IP, or with a specific request tag).
- **Difference:** The `resources` value changes from `["*"]` to a list of explicit resource ARNs, or a `condition` block is added. The key is that write access is no longer granted unconditionally to every resource in the account.
- **Why it matters:** Without constraints, a compromised identity could create or modify any Lambda function, event source mapping, or DynamoDB table, leading to data tampering, resource hijacking, or privilege escalation.

**CKV_AWS_356 – IAM policy uses `"*"` as resource for restrictable actions (policy `pass`)**

- **Current behavior:** The same `Allow` statement uses `resources = ["*"]` for actions (`lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, `dynamodb:CreateTable`) that are considered “restrictable” (i.e., they should be scoped to specific resources).
- **Satisfying configuration:** The `resources` field would list the exact ARNs of the Lambda functions and DynamoDB tables that the identity is allowed to create or manage, rather than a wildcard.
- **Difference:** The `resources` field changes from `["*"]` to a list of specific ARNs. This ensures the policy follows the principle of least privilege by only granting the action on the intended resources.
- **Why it matters:** A wildcard resource allows the action on any existing or future resource of that type, which can be exploited to create or modify resources in unintended ways, leading to data loss, privilege escalation, or resource abuse.

**CKV_AWS_108 – IAM policy allows data exfiltration (policy `fail`)**

- **Current behavior:** The policy allows `s3:GetObject` on `"*"`, meaning the identity can read any object from any S3 bucket in the account.
- **Satisfying configuration:** The `resources` field would be restricted to the specific bucket ARNs (e.g., `arn:aws:s3:::my-bucket/*`) that the identity legitimately needs to read, or a condition would be added to limit access (e.g., based on source VPC, tags, or object prefix).
- **Difference:** The `resources` value changes from `["*"]` to a list of explicit bucket ARNs. This prevents the identity from reading sensitive data from other buckets.
- **Why it matters:** Unrestricted `s3:GetObject` allows an attacker to exfiltrate any data stored in S3, which is a classic data exfiltration vector.

**CKV_AWS_107 – IAM policy allows credentials exposure (policy `fail`)**

- **Current behavior:** The policy allows `iam:CreateAccessKey` on `"*"`, which permits creating access keys for any IAM user in the account.
- **Satisfying configuration:** The `resources` field would be restricted to the specific IAM user ARNs for which key creation is necessary, or the action would be removed entirely if not needed. Alternatively, a condition could be added to restrict usage (e.g., only for users with a specific tag).
- **Difference:** The `resources` field changes from `["*"]` to a list of explicit IAM user ARNs. This limits the ability to create credentials to only those users that require it.
- **Why it matters:** Allowing `iam:CreateAccessKey` on `*` enables an attacker to create new access keys for any user, including privileged ones, and then use those keys to gain persistent access to the account.

**CKV_AWS_356 – IAM policy uses `"*"` as resource for restrictable actions (policy `fail`)**

- **Current behavior:** The policy uses `resources = ["*"]` for `s3:GetObject` and `iam:CreateAccessKey`, both of which are restrictable actions.
- **Satisfying configuration:** The `resources` field would be changed to specific ARNs (e.g., `arn:aws:s3:::my-bucket/*` and `arn:aws:iam::123456789012:user/username`).
- **Difference:** Replacing the wildcard `"*"` with explicit resource ARNs ensures that the permissions are scoped to the minimum necessary resources.
- **Why it matters:** Wildcard resources for these actions violate the principle of least privilege and expose the account to data exfiltration and privilege escalation.

**CKV_AWS_109 – IAM policy allows permissions management / resource exposure without constraints (policy `fail`)**

- **Current behavior:** The policy grants `iam:CreateAccessKey` on `"*"` without any conditions. This is a permissions management action that can expose or create credentials.
- **Satisfying configuration:** The policy would either remove the `iam:CreateAccessKey` action, restrict its resource to specific IAM users, or add a condition (e.g., `aws:SourceIp`, `aws:RequestedRegion`) that limits when the action can be performed.
- **Difference:** The `resources` field is changed from `["*"]` to a list of specific IAM user ARNs, or a `condition` block is added. This prevents unrestricted credential creation.
- **Why it matters:** Unconstrained permissions management actions allow an attacker to create, modify, or delete security credentials, leading to full account compromise.

**CKV_AWS_110 – IAM policy allows privilege escalation (policy `fail`)**

- **Current behavior:** The policy allows `iam:CreateAccessKey` on `"*"`. This action can be used to create access keys for a higher‑privileged user, enabling privilege escalation.
- **Satisfying configuration:** The policy would either remove the `iam:CreateAccessKey` action, restrict it to a specific IAM user ARN, or add a condition that limits its use (e.g., only for the user’s own account via `aws:username`).
- **Difference:** The `resources` field is changed from `["*"]` to a specific IAM user ARN, or a condition is added. This prevents the identity from creating keys for arbitrary users.
- **Why it matters:** Unrestricted `iam:CreateAccessKey` is a well‑known privilege escalation path; an attacker can create a new access key for an administrative user and gain full control of the account.

**Summary for the engineer:**

All flagged issues stem from the same root cause: **IAM policy statements that use `resources = ["*"]` for sensitive actions without any conditions.** To resolve them, you must apply the principle of least privilege:

- For the **`pass` policy** (lines 42‑56): Replace `resources = ["*"]` with the exact ARNs of the Lambda functions and DynamoDB tables that the identity should be allowed to create. If the identity truly needs to create any of these resources, add a condition that restricts the creation (e.g., based on tags, source VPC, or requiring a specific naming pattern). This will satisfy both CKV_AWS_111 and CKV_AWS_356.

- For the **`fail` policy** (lines 60‑73):  
  - Change the `s3:GetObject` resource from `"*"` to the specific bucket ARNs (e.g., `arn:aws:s3:::my-bucket/*`). This fixes CKV_AWS_108 and the S3 part of CKV_AWS_356.  
  - Change the `iam:CreateAccessKey` resource from `"*"` to the specific IAM user ARN(s) that require key creation, or remove the action entirely if it is not needed. This fixes CKV_AWS_107, CKV_AWS_109, CKV_AWS_110, and the IAM part of CKV_AWS_356.  
  - If you must keep a broader resource scope, add a condition (e.g., `StringEquals` on `aws:PrincipalTag` or `IpAddress`) to constrain the access.

The critical difference is moving from a wildcard resource to a scoped set of ARNs (or adding conditions), which directly prevents the policy from being abused for data theft, credential exposure, or privilege escalation.
