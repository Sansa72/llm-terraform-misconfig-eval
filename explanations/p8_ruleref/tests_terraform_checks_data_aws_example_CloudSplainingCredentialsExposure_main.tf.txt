## Findings on `aws_iam_policy_document.pass` (lines 42–56)

This policy allows three actions on all resources (`"*"`):

```hcl
actions = [
  "lambda:CreateFunction",
  "lambda:CreateEventSourceMapping",
  "dynamodb:CreateTable",
]
resources = ["*"]
```

### CKV_AWS_111 – Write access without constraints
**What the rule checks:** IAM policies should not grant write‑level permissions (like `Create*`, `Put*`, `Delete*`) without additional conditions that limit *who* can perform the action or *from where*. Unconstrained write access could allow an attacker to create or modify resources arbitrarily if the associated principal is compromised.

**Why it fires here:**  
- `lambda:CreateFunction` and `dynamodb:CreateTable` are write actions.  
- The resource is `"*"` – meaning the principal can create functions/tables in any region/account.  
- There are no `condition` blocks (e.g., requiring MFA, a specific source IP, or VPC endpoint).  

**Remediation:**  
- Restrict the resource to specific ARNs (e.g., `arn:aws:lambda:us-east-1:123456789012:function/my-prefix-*`).  
- Add a condition that limits access, such as `aws:RequestedRegion`, `aws:SourceIp`, or `aws:MultiFactorAuthPresent`.  
- If the actions must be broad, consider splitting them into separate statements with tighter resource constraints.

### CKV_AWS_356 – `"*"` as a resource for restrictable actions
**What the rule checks:** Certain IAM actions can be scoped to specific resources (e.g., a particular Lambda function, a DynamoDB table). Using `"*"` for those actions grants permission to *all* resources of that type, which is rarely necessary and violates least privilege.

**Why it fires here:**  
- `lambda:CreateFunction` and `dynamodb:CreateTable` are resource‑level permissions; you can specify a function name or table name in the resource ARN.  
- The policy uses `"*"`, so it allows creating functions/tables with any name in any account (if cross‑account).  
- `lambda:CreateEventSourceMapping` is also restrictable to specific function ARNs.

**Remediation:**  
Replace `"*"` with the actual ARNs of the resources the principal should be able to create. For example:
```hcl
resources = [
  "arn:aws:lambda:us-east-1:123456789012:function:my-prefix-*",
  "arn:aws:dynamodb:us-east-1:123456789012:table/my-prefix-*"
]
```
If the principal only needs to create event source mappings for a specific function, scope it to that function’s ARN.

## Findings on `aws_iam_policy_document.fail` (lines 60–73)

This policy grants two dangerous actions on `"*"`:

```hcl
actions = [
  "s3:GetObject",
  "iam:CreateAccessKey"
]
resources = ["*"]
```

### CKV_AWS_108 – Data exfiltration
**What the rule flags:** Actions that allow reading sensitive data (e.g., `s3:GetObject`, `dynamodb:Scan`) without resource or condition restrictions. An attacker with these permissions could exfiltrate data from any S3 bucket the principal can access.

**In your file:** `s3:GetObject` on `"*"` means the principal can download objects from **every** S3 bucket in the account. This is a classic data exfiltration vector.

### CKV_AWS_107 – Credentials exposure
**What the rule flags:** Actions that allow creating, modifying, or viewing IAM access keys, passwords, or other long‑term credentials. If abused, an attacker can generate permanent credentials for any IAM user and then use them outside the normal session.

**In your file:** `iam:CreateAccessKey` on `"*"` lets the principal create access keys for **any IAM user** (including highly privileged ones). This directly enables credential theft and persistence.

### CKV_AWS_109 – Permissions management / resource exposure without constraints
**What the rule flags:** IAM actions that manage permissions (e.g., `iam:CreateAccessKey`, `iam:AttachUserPolicy`) or expose resources when used with `"*"` and no conditions. These actions can be abused to escalate privileges or expose sensitive resources.

**In your file:** `iam:CreateAccessKey` is a permissions‑management action. Combined with `"*"` and no conditions, it allows the principal to create access keys for any IAM user, effectively granting them the same permissions as that user.

### CKV_AWS_110 – Privilege escalation
**What the rule flags:** IAM actions that could allow a user to elevate their own privileges (e.g., creating a new access key for a more privileged user, attaching a policy, updating a login profile).  

**In your file:** `iam:CreateAccessKey` is a well‑known privilege escalation vector. If the principal has lower privileges but can create an access key for an admin user, they can then assume that admin’s permissions.

### CKV_AWS_356 – `"*"` as a resource for restrictable actions (again)
Both `s3:GetObject` and `iam:CreateAccessKey` are resource‑restrictable (you can limit `s3:GetObject` to specific buckets/prefixes, and `iam:CreateAccessKey` to specific IAM users). Using `"*"` violates the same principle as above.

---

## How to fix the `fail` policy

1. **Remove unnecessary actions.** If the principal does not genuinely need `s3:GetObject` or `iam:CreateAccessKey`, delete them.
2. **Scope resources tightly.**  
   - For `s3:GetObject`, specify the exact bucket and optional prefix:  
     `"arn:aws:s3:::my-bucket/prefix/*"`  
   - For `iam:CreateAccessKey`, restrict to a specific IAM user or role ARN:  
     `"arn:aws:iam::123456789012:user/username"`  
   - Never use `"*"` for these actions.
3. **Add conditions.** Even with scoped resources, enforce conditions like MFA, source IP, or VPC endpoints to further reduce risk. For example:
   ```hcl
   condition {
     test     = "Bool"
     variable = "aws:MultiFactorAuthPresent"
     values   = ["true"]
   }
   ```
4. **Consider using separate statements** if different actions need different resource scopes.
