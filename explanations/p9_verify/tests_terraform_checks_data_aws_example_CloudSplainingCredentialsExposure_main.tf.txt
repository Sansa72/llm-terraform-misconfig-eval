The Terraform configuration contains two IAM policy documents that introduce significant security risks due to overly permissive resource wildcards combined with sensitive actions. Both policies are flagged by multiple checks.

**Policy `data.aws_iam_policy_document.pass` (lines 42–56)**

This policy grants `lambda:CreateFunction`, `lambda:CreateEventSourceMapping`, and `dynamodb:CreateTable` on resource `"*"`.  
- **CKV_AWS_111**: The actions are write operations, and the resource is `"*"` without any condition, allowing unrestricted creation of Lambda functions, event source mappings, and DynamoDB tables across the entire account.  
- **CKV_AWS_356**: The policy uses `"*"` as the resource for actions that are considered “restrictable” (i.e., they can and should be scoped to specific resources).  

**Policy `data.aws_iam_policy_document.fail` (lines 60–73)**

This policy allows `s3:GetObject` and `iam:CreateAccessKey` on resource `"*"`.  
- **CKV_AWS_108 (data exfiltration)**: `s3:GetObject` on `"*"` permits reading any object in any S3 bucket, enabling potential data exfiltration.  
- **CKV_AWS_107 (credentials exposure)**: `iam:CreateAccessKey` on `"*"` allows creating access keys for any IAM user, which can lead to credential exposure and account takeover.  
- **CKV_AWS_356 (wildcard resource for restrictable actions)**: Both actions are granted on `"*"`.  
- **CKV_AWS_109 (permissions management without constraints)**: `iam:CreateAccessKey` is a permissions management action that, when unrestricted, can expose or escalate privileges.  
- **CKV_AWS_110 (privilege escalation)**: `iam:CreateAccessKey` can be used to generate credentials for a higher-privileged user, enabling privilege escalation.

**Remediation**

For both policies, replace the wildcard resource `"*"` with specific resource ARNs. For the first policy, scope the `lambda:Create*` and `dynamodb:CreateTable` actions to the intended functions and tables. For the second policy, restrict `s3:GetObject` to the exact bucket and object prefix required, and either remove `iam:CreateAccessKey` entirely or restrict it to a specific IAM user path/ARN and add a strong condition (e.g., `aws:SourceIp`, `aws:RequestTag`) to limit who can create keys and for whom. Never grant sensitive IAM or data-access actions on `"*"` without strict conditions.
