The scanner identified multiple security misconfigurations across both CloudFront distributions. The `pass` distribution includes a `default_root_object`, but both distributions share the same critical issues. Below is a breakdown of each finding, the specific misconfiguration in the Terraform code, and the required remediation.

---

### 1. Viewer Protocol Policy (CKV_AWS_34)
**Problem:** The `default_cache_behavior` in both distributions sets `viewer_protocol_policy = "allow-all"`, which permits unencrypted HTTP connections.  
**Fix:** Change the policy to `"redirect-to-https"` or `"https-only"` to enforce encrypted traffic.  
**Affected code (both resources):**
```hcl
default_cache_behavior {
  ...
  viewer_protocol_policy = "allow-all"   # <-- insecure
}
```
**Remediation:**
```hcl
viewer_protocol_policy = "redirect-to-https"
```

---

### 2. Minimum TLS Version (CKV_AWS_174)
**Problem:** The `viewer_certificate` block does not specify a `minimum_protocol_version`, so it defaults to TLSv1.0. The scanner requires at least TLSv1.2.  
**Fix:** Explicitly set `minimum_protocol_version = "TLSv1.2_2021"` (or a higher policy).  
**Affected code (both resources):**
```hcl
viewer_certificate {
  cloudfront_default_certificate = true
  # minimum_protocol_version is missing
}
```
**Remediation:**
```hcl
viewer_certificate {
  cloudfront_default_certificate = true
  minimum_protocol_version      = "TLSv1.2_2021"
}
```

---

### 3. WAF Integration (CKV_AWS_68)
**Problem:** Neither distribution has a `web_acl_id` attribute, meaning no AWS WAF web ACL is associated.  
**Fix:** Attach a WAF web ACL (classic or WAFv2) by providing its ARN in the `web_acl_id` argument.  
**Affected code (both resources):** The `aws_cloudfront_distribution` blocks lack a `web_acl_id` line.  
**Remediation (example):**
```hcl
resource "aws_cloudfront_distribution" "pass" {
  ...
  web_acl_id = aws_wafv2_web_acl.example.arn
  ...
}
```

---

### 4. Origin Failover (CKV_AWS_310)
**Problem:** Each distribution defines only a single `origin` block. Without a second origin and an origin group, failover is not configured.  
**Fix:** Add a secondary origin (e.g., a backup S3 bucket) and create an `aws_cloudfront_origin_access_control` for it, then define an `origin_group` with a failover criteria.  
**Affected code (both resources):** Only one `origin` block exists.  
**Remediation:** Add a second origin and an `origin_group` block:
```hcl
origin {
  domain_name = aws_s3_bucket.backup.bucket_regional_domain_name
  origin_id   = "backup-origin"
  ...
}

origin_group {
  origin_id = "primary-origin-group"
  failover_criteria {
    status_codes = [500, 502, 503, 504]
  }
  member {
    origin_id = local.s3_origin_id
  }
  member {
    origin_id = "backup-origin"
  }
}
```
Then reference the origin group in cache behaviors via `target_origin_id`.

---

### 5. Default Root Object (CKV_AWS_305) – `fail` distribution only
**Problem:** The `fail` distribution does not set `default_root_object`, so requests to the root path may not return a default document.  
**Fix:** Add `default_root_object = "index.html"` (or an appropriate object).  
**Affected code (`fail` resource):** The attribute is absent.  
**Remediation:**
```hcl
resource "aws_cloudfront_distribution" "fail" {
  ...
  default_root_object = "index.html"
  ...
}
```

---

### 6. Custom SSL Certificate (CKV2_AWS_42)
**Problem:** Both distributions use the default CloudFront certificate (`cloudfront_default_certificate = true`) instead of a custom certificate, which is required for using custom domain names securely.  
**Fix:** Provision an ACM certificate in us-east-1, reference it via `acm_certificate_arn`, and set `cloudfront_default_certificate = false`. Also ensure `aliases` match the certificate’s domain names.  
**Affected code (both resources):**
```hcl
viewer_certificate {
  cloudfront_default_certificate = true
}
```
**Remediation:**
```hcl
viewer_certificate {
  acm_certificate_arn      = aws_acm_certificate.example.arn
  ssl_support_method       = "sni-only"
  minimum_protocol_version = "TLSv1.2_2021"
}
```

---

### 7. Response Headers Policy (CKV2_AWS_32)
**Problem:** No `response_headers_policy_id` is attached to any cache behavior, missing the opportunity to add security headers (e.g., HSTS, Content-Security-Policy).  
**Fix:** Create an `aws_cloudfront_response_headers_policy` and reference its ID in each cache behavior.  
**Affected code (both resources):** `default_cache_behavior` and `ordered_cache_behavior` blocks lack `response_headers_policy_id`.  
**Remediation:**
```hcl
resource "aws_cloudfront_response_headers_policy" "security_headers" {
  name = "security-headers"
  security_headers_config {
    content_type_options {
      override = true
    }
    frame_options {
      frame_option = "DENY"
      override     = true
    }
    # ... other headers
  }
}

# In each cache behavior:
default_cache_behavior {
  ...
  response_headers_policy_id = aws_cloudfront_response_headers_policy.security_headers.id
}
```

---

### 8. WAFv2 WebACL with AMR for Log4j (CKV2_AWS_47)
**Problem:** The distributions lack a WAFv2 web ACL, and even if one were attached, it must include AWS Managed Rules (AMR) for Log4j vulnerability (e.g., `AWSManagedRulesKnownBadInputsRuleSet` or the specific Log4j rule set).  
**Fix:** Attach a WAFv2 web ACL that contains the appropriate managed rule group.  
**Remediation:** After creating a WAFv2 web ACL with the required rules, set `web_acl_id` as shown in item 3.

---

All findings except the missing default root object apply to both distributions. Addressing these issues will bring the CloudFront configurations into compliance with the scanner’s security requirements.
