## Remediation Briefing

Below are the failing checks in the order reported by the scanner. For each, the exact trigger location, the evidenced misconfiguration, and the required change are described.

---

### 1. CKV_AWS_356 on `aws_iam_policy_document.pass` (lines 3–15)

- **Trigger:** The `statement` block at lines 5–13, specifically `resources = ["*"]` combined with `actions = ["s3:Describe*"]`.
- **What is wrong:** The policy uses a wildcard `"*"` as the resource for `s3:Describe*` actions, which are resource‑level permissions. This grants those actions on **all** S3 resources, exceeding the principle of least privilege.
- **Why it matters (from the finding):** The check ensures no IAM policy document allows `"*"` as a statement’s resource for restrictable actions. The current policy does exactly that.
- **Required change:** Replace the wildcard resource with the specific ARN(s) of the S3 bucket(s) or objects that need to be described. If the intent is to allow describing multiple buckets, list each ARN explicitly. If describing objects, consider using a condition key (e.g., `s3:prefix`) to further limit scope.

---

### 2. CKV_AWS_108 on `aws_iam_policy_document.fail` (lines 43–55)

- **Trigger:** The `statement` block at lines 45–53, with `effect = "Allow"`, `actions = ["*"]`, `resources = ["*"]`.
- **What is wrong:** The policy allows all actions on all resources, which includes data access actions (e.g., `s3:GetObject`, `dynamodb:Scan`) that can be used to exfiltrate data.
- **Why it matters:** The check prohibits IAM policies that allow data exfiltration. The wildcard actions and resources directly enable it.
- **Required change:** Restrict the `actions` list to only the specific actions required (e.g., read‑only actions if data retrieval is needed) and limit `resources` to the exact ARNs of the data stores. Avoid any wildcard that could grant access to unintended data.

---

### 3. CKV_AWS_111 on `aws_iam_policy_document.fail` (lines 43–55)

- **Trigger:** Same `statement` block (lines 45–53) with `actions = ["*"]` and `resources = ["*"]`.
- **What is wrong:** The policy grants unrestricted write access (e.g., `s3:PutObject`, `iam:CreateUser`) on all resources without any constraints.
- **Why it matters:** The check requires that write access be constrained. The current policy imposes no limits.
- **Required change:** Remove wildcard actions. List only the necessary write actions, and scope `resources` to the specific ARNs that should be writable. Add conditions (e.g., `aws:RequestedRegion`, `s3:prefix`) if further restriction is needed.

---

### 4. CKV_AWS_49 on `aws_iam_policy_document.fail` (lines 43–55)

- **Trigger:** The `actions = ["*"]` line (line 48) inside the `statement` block.
- **What is wrong:** The policy uses `"*"` as the action, granting permission to perform any AWS action.
- **Why it matters:** The check forbids IAM policy documents that allow `"*"` as a statement’s actions. This is a direct violation.
- **Required change:** Replace `"*"` with an explicit list of the exact actions required. Never use a wildcard for actions unless absolutely unavoidable and justified.

---

### 5. CKV_AWS_107 on `aws_iam_policy_document.fail` (lines 43–55)

- **Trigger:** The same `statement` block, because `actions = ["*"]` includes credential‑related actions (e.g., `iam:CreateAccessKey`, `sts:AssumeRole`).
- **What is wrong:** The policy allows actions that can expose or create long‑term credentials.
- **Why it matters:** The check ensures IAM policies do not allow credentials exposure. The wildcard action permits such exposure.
- **Required change:** Remove any actions that manage or expose credentials from the allowed list. If credential actions are genuinely needed, restrict them to specific resources and add strong conditions (e.g., MFA, source IP). In most cases, they should not be present.

### 6. CKV_AWS_356 on `aws_iam_policy_document.fail` (lines 43–55)

### 7. CKV_AWS_109 on `aws_iam_policy_document.fail` (lines 43–55)
