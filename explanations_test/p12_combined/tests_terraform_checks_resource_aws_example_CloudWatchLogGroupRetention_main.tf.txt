## Remediation Briefing: CloudWatch Log Group Misconfigurations

The scanner identified five failing checks across two `aws_cloudwatch_log_group` resources. Below is a check-by-check breakdown of what is wrong, why it matters, and the change required to pass. All evidence is drawn solely from the provided Terraform file and scanner findings.

---

### 1. CKV_AWS_338 on `aws_cloudwatch_log_group.pass` (lines 1–3)

**What triggers it:**  
Line 2 sets `retention_in_days = 3`.

**What is wrong and why it matters:**  
The retention period is 3 days, which is less than the required 365 days (1 year). Logs would be automatically deleted after 3 days, making them unavailable for long-term auditing, compliance, or incident investigation.

**Change needed:**  
Increase the `retention_in_days` argument to a value of 365 or greater. For example, set it to `365` to meet the minimum 1-year retention requirement.

---

### 2. CKV_AWS_158 on `aws_cloudwatch_log_group.pass` (lines 1–3)

**What triggers it:**  
The resource block (lines 1–3) does not include a `kms_key_id` argument.

**What is wrong and why it matters:**  
No customer-managed KMS key is specified, so log data is not encrypted using a key you control. This may violate encryption requirements for sensitive log data.

**Change needed:**  
Add a `kms_key_id` argument referencing the ARN of an existing KMS key. This will enable encryption at rest for the log group.

---

### 3. CKV_AWS_66 on `aws_cloudwatch_log_group.fail` (line 5)

**What triggers it:**  
The resource block at line 5 is empty (`{}`); no `retention_in_days` is set.

**What is wrong and why it matters:**  
The retention period is not explicitly defined. While the default behaviour is to never expire logs, the check requires an explicit retention setting to avoid indefinite storage (which can lead to uncontrolled cost growth and non-compliance with data lifecycle policies).

**Change needed:**  
Add a `retention_in_days` argument with a valid number of days (e.g., 365) to explicitly define how long logs are kept.

---

### 4. CKV_AWS_338 on `aws_cloudwatch_log_group.fail` (line 5)

**What triggers it:**  
The resource block at line 5 has no `retention_in_days` argument.

**What is wrong and why it matters:**  
Without an explicit retention setting, the requirement to retain logs for at least 1 year is not satisfied. The check demands a configured retention period of 365 days or more.

**Change needed:**  
Set `retention_in_days` to a value of 365 or higher. This will both satisfy the explicit retention requirement and meet the 1-year minimum.

---

### 5. CKV_AWS_158 on `aws_cloudwatch_log_group.fail` (line 5)

**What triggers it:**  
The resource block at line 5 does not contain a `kms_key_id` argument.

**What is wrong and why it matters:**  
Log data is not encrypted with a customer-managed KMS key, leaving encryption to the default (AWS-managed) key or no encryption, which may not meet security standards.

**Change needed:**  
Add a `kms_key_id` argument with the ARN of a KMS key to enable customer-managed encryption for this log group.

---

All changes are straightforward attribute additions or value adjustments. Apply them to the respective resources to clear every failing check.
