**Remediation briefing**

Below are the failing checks in the order they appear in the scanner output. For each, I identify the resource, the exact lines that trigger the finding, what is wrong, and the change required to make the check pass.

---

### 1. CKV_AWS_323 on `aws_elasticache_cluster.enabled` (lines 3–11)

**Trigger:** The resource block at lines 3–11 does not include a `subnet_group_name` argument.  
**What is wrong:** The cluster will be placed in the default subnet group for the VPC. The default subnet group typically spans all subnets in the VPC, which may include public subnets and subnets not intended for ElastiCache, increasing the network exposure of the cluster.  
**Change needed:** Add a `subnet_group_name` argument that references a dedicated ElastiCache subnet group containing only the private subnets where the cluster should reside.

---

### 2. CKV_AWS_134 on `aws_elasticache_cluster.default` (lines 15–21)

**Trigger:** The resource block at lines 15–21 omits the `snapshot_retention_limit` argument.  
**What is wrong:** For a Redis cluster, the absence of `snapshot_retention_limit` (or its default of `0`) means automatic backups are disabled. This removes the ability to recover data automatically in case of failure or corruption.  
**Change needed:** Set `snapshot_retention_limit` to a positive integer (e.g., `5`) to enable automatic daily backups and retain them for the specified number of days.
