**Remediation Briefing**

Below are the findings, grouped by the Terraform resource they affect, in the order presented by the scanner. Each entry names the check and resource, states the problem in one line, explains why it matters, and describes the change needed to pass the check.

---

### 1. CKV_AWS_356 on `aws_iam_policy_document.pass` (lines 3–15)

**What is wrong:** The policy statement uses `"*"` as the resource for an action that is resource‑restrictable.  
**Why it matters:** Granting a resource‑restrictable action (like `s3:Describe*`) on all resources (`"*"`) violates the principle of least privilege. If the associated role is compromised, the attacker can describe any S3 resource in the account, potentially mapping the entire storage footprint.  
**Change needed:** Replace the wildcard resource with the specific ARN(s) of the S3 bucket(s) that the policy is intended to cover. For example, if the policy should only allow describing a particular bucket, set `resources = ["arn:aws:s3:::my-bucket"]`. If the action truly does not support resource‑level permissions (e.g., `s3:DescribeJob` is a resource‑level action, but some `s3:Describe*` actions might not be), verify the action’s resource type in the IAM documentation and scope the resource accordingly. If the action is not resource‑level, the resource must remain `"*"`; in that case, consider adding a `Condition` block to restrict access by source IP, VPC, or tags to reduce the effective scope.

### 2. CKV_AWS_108 on `aws_iam_policy_document.fail` (lines 43–55) – Data exfiltration

**What is wrong:** The policy allows `"*"` actions on `"*"` resources, which includes actions that can exfiltrate data (e.g., `s3:GetObject`, `rds:Describe*` with download capabilities).  
**Why it matters:** An identity with this policy can read and copy sensitive data from any service, leading to a data breach.  
**Change needed:** Replace the wildcard action with a tightly scoped list of specific actions that are necessary for the intended workload. Explicitly exclude data‑read actions that are not required. Similarly, restrict the resource element to the exact ARNs of the resources the identity needs to access.

---

### 3. CKV_AWS_111 on `aws_iam_policy_document.fail` (lines 43–55) – Write access without constraints

**What is wrong:** The policy grants unrestricted write access (`"*"` actions on `"*"` resources).  
**Why it matters:** Unconstrained write permissions allow an attacker to modify, delete, or corrupt data, create resources, or inject malicious configurations.  
**Change needed:** Replace the wildcard action with a minimal set of write actions that are absolutely required. For each allowed write action, scope the resource to the specific ARNs that need to be modified. Add conditions (e.g., `aws:RequestedRegion`, `s3:x-amz-acl`) to further limit write operations.

---

### 4. CKV_AWS_49 on `aws_iam_policy_document.fail` (lines 43–55) – No wildcard actions

**What is wrong:** The statement uses `"*"` as the action, granting permission to perform any action in AWS.  
**Why it matters:** This is the most dangerous IAM misconfiguration; it effectively gives the principal full administrative rights over all resources in the account.  
**Change needed:** Replace `"*"` with a specific, limited list of allowed actions. Follow the principle of least privilege: only include the exact actions required for the workload.

---

### 5. CKV_AWS_107 on `aws_iam_policy_document.fail` (lines 43–55) – Credentials exposure

**What is wrong:** The wildcard action includes IAM actions that can expose or create access keys, passwords, and other credentials.  
**Why it matters:** An attacker could create new access keys, retrieve existing ones, or generate service‑specific credentials, leading to persistent unauthorised access.  
**Change needed:** Remove any IAM actions that manage credentials (e.g., `iam:CreateAccessKey`, `iam:UpdateLoginProfile`) from the allowed actions. If credential management is required, restrict it to specific IAM users/roles using resource ARNs and conditions.

### 6. CKV_AWS_356 on `aws_iam_policy_document.fail` (lines 43–55) – Resource wildcard for restrictable actions

**What is wrong:** The policy uses `"*"` as the resource for actions that support resource‑level permissions.  
**Why it matters:** Even if the action list is later scoped, leaving the resource as `"*"` for restrictable actions still grants access to all resources of that type, which is overly permissive.  
**Change needed:** After narrowing the actions, set the resource element to the specific ARNs of the resources that the principal needs to access. For any action that does not support resource‑level permissions, the resource must remain `"*"`, but those actions should be isolated in a separate statement with appropriate conditions.

### 7. CKV_AWS_109 on `aws_iam_policy_document.fail` (lines 43–55) – Permissions management without constraints

**What is wrong:** The policy allows IAM actions (implied by `"*"`) that can create, modify, or delete IAM users, roles, and policies.  
**Why it matters:** Unrestricted permissions management enables privilege escalation and can lead to full account takeover.  
**Change needed:** Remove all IAM management actions unless absolutely necessary. If IAM management is required, restrict it to specific roles/users and use conditions (e.g., `iam:PassedToService`) to limit the scope. Never grant `iam:*` or `"*"` that includes IAM write actions.
