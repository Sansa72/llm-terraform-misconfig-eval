## Remediation Briefing

Below are the failing checks in the order reported by the scanner. For each, a one‑line summary of the problem, its security importance, and a prose description of the required change are given. Where fixes interact across resources, this is noted.

---

### CKV_AWS_150 on `aws_lb.enabled` (lines 3‑10)
**What’s wrong:** Deletion protection is not enabled on this Application Load Balancer.  
**Why it matters:** Without deletion protection, the load balancer can be deleted accidentally (e.g., via API call, console misclick, or automation error), causing a service outage.  
**Change needed:** Add the attribute `enable_deletion_protection = true` to the `aws_lb` resource block. This will prevent accidental deletion unless the attribute is explicitly set back to `false` before a destroy operation.

---

### CKV_AWS_91 on `aws_lb.enabled` (lines 3‑10)
**What’s wrong:** Access logging is not configured for this Application Load Balancer.  
**Why it matters:** Access logs record detailed information about requests sent to the load balancer, which is essential for security analysis, troubleshooting, and compliance auditing.  
**Change needed:** Add an `access_logs` block inside the resource. The block must specify an S3 bucket (`bucket`) and optionally a prefix (`prefix`). The bucket must already exist and have a policy granting the load balancer’s account permission to write logs. The same bucket can be reused for all load balancers, but each resource needs its own `access_logs` block.

**Change needed:** Add `enable_deletion_protection = true` to the `aws_alb` resource. (Note: `aws_alb` is functionally identical to `aws_lb`; the fix is the same.)

### CKV2_AWS_28 on `aws_lb.enabled` (lines 3‑10)
**What’s wrong:** This public‑facing Application Load Balancer is not associated with a WAF web ACL.  
**Why it matters:** Without a WAF, the application is exposed to common web exploits like SQL injection, cross‑site scripting, and bot attacks.  
**Change needed:** Create (or reference an existing) `aws_wafv2_web_acl` resource, then add an `aws_wafv2_web_acl_association` resource that links the ALB’s ARN to the web ACL’s ARN. The same web ACL can be shared across multiple ALBs, but each ALB requires its own association resource.

### Interactions and Shared Dependencies
- **Deletion protection** (`enable_deletion_protection`) is a simple boolean attribute that can be added independently to every load balancer resource. No cross‑resource conflicts.
- **Access logging** (`access_logs`) requires an S3 bucket. All load balancers can share the same bucket, but each must have its own `access_logs` block. Ensure the bucket policy allows the ELB service principal for the account to write logs.
- **Drop invalid headers** (`drop_invalid_header_fields`) is only relevant for Application Load Balancers. The `enabled` resources already have it set correctly; the `default` and `disabled` resources need it added or corrected.
- **Cross‑zone load balancing** for the Network LB is a single attribute addition. The Gateway LB finding is a false positive and should be suppressed.
- **WAF association** requires a WAFv2 web ACL to exist first. All six public‑facing ALBs can be associated with the same web ACL, but each needs its own `aws_wafv2_web_acl_association` resource. The web ACL itself can be defined once and referenced by ARN.
