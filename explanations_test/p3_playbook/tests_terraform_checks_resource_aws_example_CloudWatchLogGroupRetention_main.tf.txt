**Remediation briefing: CloudWatch log group misconfigurations**

Below are the failing checks in the order reported, with the required changes described in prose. No complete Terraform blocks are provided; apply the changes to the existing resources.

---

### 1. CKV_AWS_338 on `aws_cloudwatch_log_group.pass` (lines 1‑3)
**What is wrong:** The log group is configured with `retention_in_days = 3`, which is far below the required minimum of 365 days.  
**Why it matters:** Logs that are deleted too quickly cannot be used for security investigations, incident forensics, or compliance audits that mandate a one‑year retention period.  
**Change needed:** Modify the `retention_in_days` argument to a value of 365 or greater (e.g., 365, 400, or 731). This single change will satisfy the check.

---

### 2. CKV_AWS_158 on `aws_cloudwatch_log_group.pass` (lines 1‑3)
**What is wrong:** The log group does not specify a KMS key for encryption; it relies on the default CloudWatch encryption (which uses an AWS‑owned key, not a customer‑managed key).  
**Why it matters:** Without a customer‑managed KMS key, you lack control over key rotation, access policies, and the ability to disable the key in an emergency. Many compliance frameworks require customer‑managed encryption for sensitive log data.  
**Change needed:** Add a `kms_key_id` argument referencing the ARN of a KMS key (e.g., `aws_kms_key.my_key.arn`). Ensure the key policy grants CloudWatch Logs permission to use the key. This change is independent of the retention fix above.

---

### 3. CKV_AWS_66 on `aws_cloudwatch_log_group.fail` (line 5)
**What is wrong:** The log group has no `retention_in_days` argument, so logs are kept indefinitely (or until manually deleted).  
**Why it matters:** Indefinite retention can lead to unbounded storage costs and may violate data‑retention policies that require logs to be purged after a defined period. Explicit retention settings also make the lifecycle predictable.  
**Change needed:** Add a `retention_in_days` argument with a value appropriate for your policy. **Note:** If you set this to 365 or more, it will also resolve the CKV_AWS_338 finding for this resource (see next item). The minimum value to satisfy both checks is 365.

---

### 4. CKV_AWS_338 on `aws_cloudwatch_log_group.fail` (line 5)
**What is wrong:** The log group has no retention setting, so it does not guarantee logs are kept for at least one year.  
**Why it matters:** Same as item 1 – insufficient retention undermines auditability and incident response.  
**Change needed:** Set `retention_in_days` to 365 or higher. This is the same change required for CKV_AWS_66; applying it once will clear both findings for this resource.

---

### 5. CKV_AWS_158 on `aws_cloudwatch_log_group.fail` (line 5)
**What is wrong:** The log group is not encrypted with a customer‑managed KMS key.  
**Why it matters:** Same as item 2 – lack of customer‑managed encryption reduces control over data protection and key lifecycle.  
**Change needed:** Add a `kms_key_id` argument with the ARN of a KMS key. This change is separate from the retention fix and must be applied alongside it.

---

**Interactions:** For the `fail` resource, adding a `retention_in_days` value of 365 or more will simultaneously resolve both CKV_AWS_66 and CKV_AWS_338. The KMS encryption fix (CKV_AWS_158) is independent and must be applied to both resources.
