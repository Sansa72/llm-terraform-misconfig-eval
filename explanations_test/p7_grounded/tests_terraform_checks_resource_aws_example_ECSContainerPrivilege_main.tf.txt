### 1. CKV_AWS_336 – ECS containers should have a read-only root filesystem

**What the check requires**  
Each container definition in an ECS task should set `readonlyRootFilesystem` to `true`. This prevents processes inside the container from writing to the root filesystem, reducing the risk of malicious modifications or persistence.

**Where the problem is**  
The check was raised on both task definitions:

- **`aws_ecs_task_definition.pass`** (lines 1–41)  
- **`aws_ecs_task_definition.fail`** (lines 43–84)

In both resources, the `container_definitions` (lines 3–30 and 45–73) are defined as JSON-encoded lists of container objects. Neither container in either task definition includes the `readonlyRootFilesystem` attribute. Because the attribute is absent, the scanner correctly flags that the root filesystem is not explicitly set to read-only.

**Evidence in the file**  
- `pass` resource: container definitions at lines 3–30 – no `readonlyRootFilesystem` key.  
- `fail` resource: container definitions at lines 45–73 – no `readonlyRootFilesystem` key.

**What to do**  
Add `"readonlyRootFilesystem": true` to each container definition in both task definitions. For example, the first container in `pass` would become:

```json
{
  "name": "first",
  "image": "service-first",
  "cpu": 10,
  "memory": 512,
  "essential": true,
  "readonlyRootFilesystem": true,
  "portMappings": [
    {
      "containerPort": 80,
      "hostPort": 80
    }
  ]
}
```

Apply the same change to the second container in `pass` and both containers in `fail`.

### 2. CKV_AWS_334 – ECS containers should not be privileged

**What the check requires**  
Containers must not run with elevated privileges (`privileged` must be `false` or omitted, as the default is `false`). A privileged container has almost all the capabilities of the host machine, which breaks process isolation and increases the risk of host compromise.

**Where the problem is**  
The finding is raised only on **`aws_ecs_task_definition.fail`** (lines 43–84).  
The second container definition in that resource explicitly sets `privilege: true` on **line 64**.

**Evidence in the file**  
Lines 60–70 of the `fail` resource:

```terraform
    {
      name      = "second"
      image     = "service-second"
      cpu       = 10
      memory    = 256
      essential = true
      privilege = true          # <-- line 64
      portMappings = [
        {
          containerPort = 443
          hostPort      = 443
        }
      ]
    }
```

The `pass` resource does not set `privilege` on any container, so it is not flagged by this check.

**What to do**  
Remove the `privilege = true` line (or change it to `privilege = false`) from the second container in the `fail` task definition. If the container genuinely requires elevated privileges, you must document a strong justification and accept the risk; otherwise, the setting should be removed to follow the principle of least privilege.
